## 关键：项目负责人澄清架构设计（三模式 + 可独立拆分）

用户明确设计意图（与 `docs/tech/07-0.2.0.md` 一致）：
- **org = 租户**（租户中心，multi 下签发身份）；**model = 建模**；**lineage = 数据地图**

### 这修正了我之前的两个判断（重要，勿再误判）

2. **「dw-model 在 multi 下不提供登录」是设计**（方案 3.5：模块 standalone/standard 不登记不调组织），

## 多租户设计评审（只诊断，未改代码）

任务：审视 multi 模式下各服务的租户设计、上下文传递、跨服务交互是否合理。
产出 `docs/tech/multi-tenant-review.md`（含证据索引，标注 [读证]/[实测]/[推断]）。

### 核心结论
**架构意图对（org 是唯一身份源、跨服务只认 code、不共库），但隔离靠"逐端点自觉"而非结构性保证。**
根因：**JWT 里没有租户声明**（只有 sub/username/name/platform_admin/boot），
租户完全来自请求头 → 每个端点必须自己校验，忘记一次就是越权。

### 严重问题（均 [读证]）
- **F1 🔴 dw-model multi 双权威分叉**：`AccessService.requireMember` 的 multi 分支
  直接 `remoteAuthz` 并 `return`，**跳过 `requireProject`（唯一校验"项目属于当前租户"的方法）**；
  而 `remoteAuthz` 的 projectCode **优先取请求头**而非 URL 路径 → 授权判的是头里的项目、
  数据操作落在路径里的项目。加上 **dw-model 无 MyBatis-Plus TenantLineInnerInterceptor**、
  **domains 等表无 tenant_id 列**（隔离只经 project_id）、模块的 projects 表镜像了**全部租户**的项目
  → 可构造跨租户读写。附带：`saveDomain` 的 `selectById(in.id())` 不带 project 作用域（IDOR）。

## lineage JWT 鉴权：与 dw-model 实现的逐项对比（用户追问「一样吗」）

用户在我改 ProductEmbed.vue 时打断并问「这块实现和 model 一样吗」。核实结论：

**主干一样**：NimbusJwtDecoder + HS256/RS256 双路、oauth2ResourceServer().jwt()、
csrf disable + STATELESS + OPTIONS permitAll、属性结构 security.{mode,jwt-secret,casdoor.{issuer,jwk-set-uri}}、
环境变量名（SECURITY_MODE/JWT_SECRET/CASDOOR_ISSUER/CASDOOR_JWK）与默认密钥字面量全部对齐。编译 BUILD SUCCESS。

**有意不同的 4 处**
1. **模式门槛**（关键）：model = `isStandalone() ? 放行 : 需认证`（standard 也要认证，因 model 自带账号体系
   WarehouseLocalSeedRunner 灌 张三/123456）；lineage = `isMulti() ? 需认证 : 放行`（**standard 放行**，
   因 lineage 无账号体系、没人能认证）。→ lineage 的 standard 模式是完全开放的，这点需用户知晓。
2. **boot 世代校验**：model 有 JwtSessionEpoch（warehouseOnly+multi 跳过）；lineage 无 —— 校验的是组织令牌，
   boot 属组织那次启动，比对本进程会把所有令牌判过期。代价：lineage 无法靠改 epoch 失效令牌。
3. **放行清单显式性**：model 显式列 login/refresh/manifest/health/internal；lineage 的 `/internal/**`
   靠 anyRequest().permitAll() 隐式兜住（模块令牌校验在 controller 内）。功能等价、显式性差。
4. **租户上下文挂载位置**：model 是 security filter（addFilterAfter BearerTokenAuthenticationFilter）；
   lineage 是 MVC 层 HandlerInterceptor。→ lineage 缺 token 且缺租户头时返回 401 而非「缺租户头」400。

**共同缺陷（非本次遗漏）**：两边都不校验 aud/iss，只验签名；dev HS256 三个服务共用同一默认密钥。

**未接完**：lineage 前端链路完成（#boot= → sessionStorage['sql-tools.bootToken'] → currentAuthHeaders()
→ 拦截器注入 Authorization；embed.ts 已收 dw-embed-token 走 applyAccessToken，键一致）。
但**壳侧 ProductEmbed.vue 只 import AUTH_TOKEN_EVENT、声明 MSG_TOKEN，既没监听也没 postMessage**
→ token 续期目前仍只能靠 sessionKey 变化重建 iframe（丢页面状态）。client.ts 已在 setAuthToken 里
dispatchEvent(AUTH_TOKEN_EVENT, {token, tokenExp})，缺的是壳侧消费方。用户打断在此处，等其决定是否继续。

## dw-model 的令牌形态（用户追问「用的是 token 还是 jwt」）+ 新发现一个默认开放面

**三种令牌，分工不同**（`dw-model/api/.../auth/`）：
1. **access = JWT，HS256 对称签名**。`JwtIssuer.issue()` 用 `MACSigner(jwtSecret)`；
   claims = sub(userId)/username/name/platform_admin/boot(JwtSessionEpoch)，**无租户声明**；
   代码注释原文「JWT 只认人，不把当前租户当 token 真源」→ 这正是 multi-tenant 评审 F1/F3/F7 的根因。
   TTL 900s。校验走 `SecurityConfig.jwtDecoder`。
2. **refresh = 不透明随机串，不是 JWT**。`RefreshTokenService.randomRaw()` = 32B SecureRandom → Base64URL；
   落库存 **SHA-256 哈希**（`refresh_tokens.token_hash CHAR(64)` 唯一约束），明文不落库。
   为什么不用 JWT：登出/改密/踢下线要能立即失效，无状态 JWT 做不到。
3. **module token = 静态共享密钥**（就是一串口令），`X-Module-Token` 头，服务间调 `/internal/v1/**` 用。
OIDC 模式：access 仍是 JWT，但 RS256 由 Casdoor 签，model 只持公钥（JWKS）。

**新发现（🔴 默认部署下是开放面）**：`assertModule` / `assertInternal` 在 `module-token` 为空时
**整个块等价于 `return;`** —— 因为 `if (user == null || isBlank || "anonymous") return;` 之后方法就结束了，
真实用户走到最后也是放行。而三服务默认值都是 `${MODULE_TOKEN:}`（空），且 `/internal/v1/**`
在 SecurityConfig 里是 permitAll → **默认部署下 dw-model 的 `/internal/v1/projects/{code}` PUT/DELETE
任何人都能调**（multi 下会建/删项目镜像）。dw-org 同一份逻辑、同一个洞。
注释意图写的是「未配模块令牌时，本机开发允许服务间调用」，与实现不符 —— 是个伪装成守卫的空操作。
建议：非 standalone 且 module-token 为空 → 401（或启动即拒绝），把「静默开放」改成「明显失败」。

## 核实：lineage 的 standard 模式有没有认证 —— 没有，且这是「未实现」不是「有意放行」

  | 能力 | standalone | standard | multi |
  |---|---|---|---|
  | /api/** 认证 | 放行 | 放行 | 需 JWT |
  | 租户头 | 可空回落 | 可空回落 | 必填→400 |
  | 调组织 | 否 | 否 | 是 |
  | internal 模块令牌 | 豁免 | 要求 | 要求 |
- 对照 dw-model：`WarehouseLocalSeedRunner` 在 `isStandard()` 时种本地账号（张三/123456），
  SecurityConfig 是 `isStandalone() ? 放行 : 需认证` → **model 的 standard 是真有认证的**
- dw-org：`runMode()` 里 `isOrgOnly() → multi`，恒 multi

### 更正（重要）
`docs/tech/07-0.2.0.md` §3.3 规定 standard 的 `Authorization` = **本模块 JWT**；
§4 规定 `standard = 本地用户 + 本库「组织角色 + 产品角色」`。
→ **standard 带认证是设计要求，lineage 尚未实现。**

我在 ADR-0011 里把它写成「有意的角色差异 / 只能放行」——**那个定性是错的**，已更正：
- ADR-0011：新增「更正：standard 模式的定性」一节（含三模式行为表）+ 改写 Consequences 里那条
- `SecurityConfig` javadoc 加了 ⚠️ 警示（标明是未实现，且不要在别处顺手加半成品鉴权）
- `docs/overview.md` 的「注意」段改为同一表述

### 风险表述（回答用户的核心）
**把数据地图按 `standard` 独立交付 = 交付一个没有任何认证的系统。**
现在没出事，是因为「独立交付」走的是 `standalone`（无认证本来就是它设计上的样子）。
**只要这个标签还没实现，就不要对外把它当作「独立版有账号」来承诺。**

### 三个选项（未决策）
1. 实现 standard：给 lineage 加本地账号（用户表 + 密码 + 登录端点 + 签发本模块 JWT + 角色）——
   是一整块功能，不是补丁；还要动前端（登录页、token 存储）
2. 从产品上撤掉这个标签：明确 lineage 只支持 standalone / multi，配置里传 standard 直接拒绝启动
   （最诚实、最省事，且立刻消除「以为有认证」的误解）
3. 维持现状：不改代码，但在部署/销售文档里明确 standard 无认证
