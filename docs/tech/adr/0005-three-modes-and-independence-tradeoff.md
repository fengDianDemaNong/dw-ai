# ADR-0005: 「三模式 + 可独立拆分」约束下的重复取舍

## Status

Accepted（2026-09-21）· 修正 ADR-0003 中「32 类重复是技术债」的判断

## Context

项目负责人澄清了架构意图（与技术方案 `docs/tech/07-0.2.0.md` 一致）：

- **org** 做租户（组织 / 租户中心）；**model** 做建模；**lineage** 做数据地图。
- model、lineage 以及后期新增的服务都设计为**可独立拆出**：每个服务都能单独拿出来直接使用。
- 它们有**三种启动模式**：
  - `multi` —— 只有这种模式下才与 org 整合（org 签发身份、`/internal/v1` 提供 authz）
  - `standard` —— 独立服务，自带账号体系
  - `standalone` —— 独立服务，不设登录
- 各服务可组合使用（multi），也可各自独立部署。

这条约束**修正了此前两个判断**：

1. ADR-0003 把「dw-org 与 dw-model 共享 32 个组织与平台类」定性为「重复的技术债」。
   **修正**：在 standard / standalone 模式下，模型服务必须能自管组织与账号 ——
   也就是说这份代码**是「能独立拿出」的必要条件，不是残留**。
   同理，dw-model 带 31 张表（含组织表）也是刻意设计。
2. ADR-0004 把「dw-model 在 multi 下不提供登录」当成一条待固化的隐含约定。
   **确认**：这是设计（技术方案 3.5 明确「模块 standalone/standard 不登记、不调组织」，
   反过来 multi 下模块不自管登录），把它做成测试是对的，但现在有了文档依据。

## Decision

**保留「每服务自带组织领域代码」这个结构，但把它的来源从「复制」改为「依赖」**：

1. 抽 `dw-common`（组织与平台的 entity / mapper / support / dto），
   org 与 model 通过 Maven 依赖引入 —— **依赖会被打进各自的 fat jar，独立部署不受影响**。
2. 评价标准随之改变：`dw-common` 的价值不是「消技术债」，而是
   **把「新增一个可独立部署的服务」的成本，从「复制 32 个类」降为「加一行依赖」**。
   这直接服务于「后期一些服务做成独立的」这一规划。
3. 若某个服务在某模式下确实用不到组织代码（如 multi 下的 model），
   依赖仍在 jar 里但不会被调用 —— 用「多带一份约几十 KB 的 class」换取「独立可部署」。

## Consequences

变得更容易：

- 新增独立服务的边际成本大幅下降（这是本决策的主要收益）；
- 组织领域的一处修复可以同时惠及 org 与 model，不必双写。

变得更难 / 需要配套：

- `dw-common` 每次改动要重新 install，构建链路需要统一（见 P1-5）；
- 必须**保证独立可部署不被破坏** —— 建议加一条 CI 检查：
  `mvn -f <服务>/pom.xml package` 能在不访问兄弟服务的前提下产出可运行 jar。

## 由此新增/调整的优化项

| 项 | 说明 |
|---|---|
| **P0-A2 三模式冒烟测试** | 每个服务在 `standalone` / `standard` / `multi` 下都要能启动并通过基本请求。这是「可独立拿出用」这个目标**唯一可验证的方式**，目前只测了默认模式 |
| **P0-A3 跨服务契约测试** | 设计明确禁止：模块共库、前端直打兄弟 `/api`、把组织库主键当跨服务 code；并要求「`X-Tenant-Code` 解析不到 → 400，**不准静默落到租户 1**」。这些都是约定，目前无测试守着 |
| **P1-5 构建统一 + 版本对齐** | dw-lineage 停在 Spring Boot 3.3.11，另两个 3.3.13。服务要独立发布，版本应统一 |
| **P0-1b 抽 dw-common** | 动机修正（见上），优先级随「新增独立服务」的规划上升 |
