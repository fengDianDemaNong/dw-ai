# 0.1.5 技术方案：页面路由、菜单、接口路由

依据：[spec/06-runtime-modes.md](../product/versions/0.1.5/spec/06-runtime-modes.md)  
对照：[05-0.1.5-modes.md](./05-0.1.5-modes.md)  
状态：设计中。本文件是路由真源；实现与原型都按这里改，禁止各服务自己再发明第一段路径。

目标：每个模块三种模式共用**同一套路径**，用启动配置裁菜单和接口，而不是换一套 URL。以后上网关、加质量/服务进程时，不和仓建设抢 `/w`、`/api/projects`。

---

## 1. 原则

1. **进程即产品**。页面和浏览器 API 只打当前进程的 origin。浏览器不直连兄弟模块。
2. **产品码在基址，不在 path 里再写一遍**。独立端口时 path 从 `/` 起；网关挂到同域时用 `/{product}` 做 `base`（见 §8）。不要出现 `/warehouse/api/warehouse/...`。
3. **浏览器走 `/api/v1`，服务间走 `/internal/v1`。** 两套永不混用。
4. **项目 ID 不进前端 path**（表/作业等业务对象除外）。当前租户/项目在会话与 Header。租户不能自定义路由。
5. **别人的菜单不注册进自己的 Vue Router。** 仓建设不再挂 `/w/meta`、`/w/serve`。侧栏外链或 embed 指向对方 origin。
6. **每种模式只裁可见性，不改 path。** 独立没有的登录页可以不注册，但 `/app/spec/domains` 三种模式都是这一条。

## 3. 前端：第一段路径（全局冻结）

每个 SPA **只允许**下列第一段。新页面往叶子加，不许再开 `/sys`、`/w`、`/admin` 这种新树。

| 第一段 | 谁用 | 做什么 |
|---|---|---|
| `/login` | org；warehouse/metadata 的 `standard` | 登录 |
| `/auth` | 同上 | OIDC 回调 `/auth/callback` |
| `/select-tenant` | 仅 org `multi` | 选租户 |
| `/platform` | 仅 org `multi` | 平台后台 |
| `/workbench` | org；各模块 `standard` 的本地账号 | 组织/本地管理（用户、项目） |
| `/app` | 除 org 外的产品 | 项目工作台（当前项目在会话） |
| `/embed` | 除 org 外的产品 | 与 `/app` 同页去壳，给组织侧栏 iframe |
| `/no-project` | org；模块 `standard` | 已登录但没有项目 |
| `/forbidden` | 全产品 | 无权限 |

禁止：`/w`、`/sys`、`/admin`、`/org`、`/projects`（作为第一段）、`/meta`（作为仓建设第一段）。旧地址只做 **301 兼容一层**，见 §9。

路由 name：`{product}.{area}.{leaf}`，例如 `org.platform.tenants`、`warehouse.spec.domains`。

## 4. 菜单与页面

菜单 **id** 是跨进程稳定键（组织侧栏、权限、埋点都用它）。`path` 是本进程内地址。

**组织侧栏的产品菜单现在是数据，不是代码**（`nav_items` 表 + `/api/nav`）：每行是
`{product, label, icon, path, sort_order, enabled}`，`path` 存**子应用内**路径（如 `/lineage/tables`），
组织渲染时拼成完整路由 `/org/embed/{product}{path}`（见 §12）。改前那段「`href` 由组织拼
`{service.baseUrl}{path}`」的说法已作废 —— `baseUrl` 那一列连同心跳一起退役，现在拼的是
服务登记里的 `frontend_url`（产品页面地址）。

**侧栏分组也是数据**（`nav_groups` 表，管理入口在「菜单管理 → 分组管理」抽屉）。但
`nav_items.group_title` 仍是**字符串**、不建外键 —— 分组表只提供三样东西：配菜单时的候选清单、
组间顺序、空组策略（`always` 保留并置灰 / `hide` 整组隐藏）。各服务按项目分层**动态生成**的分组
（如仓建设的「建模中心」）天生进不了静态表，未登记的分组名照样能落库、照样显示，只是排在已登记的分组之后。

`mode`：`S` 独立 / `T` 普通 / `M` 多租户。空 = 三种都有。

## 5. 后端：公共约定

每个进程（含 `rules`）必须有：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 探活，无鉴权。`rules` 现有 `/health` 保留为别名 |
| GET | `/api/runtime` | `{ product, version, runMode }`，无鉴权 |
| GET | `/api/v1/manifest` | 产品码、角色、菜单 id/path/perm。独立可匿名 |

浏览器 API 一律 `/api/v1/...`。  
服务间一律 `/internal/v1/...`，校验 `module_token`，不接受用户 JWT 当模块身份。

**Header（浏览器 → 本模块）**

| Header | 独立 | 普通 | 多租户 |
|---|---|---|---|
| `Authorization: Bearer` | 可选静态令牌 | 本地 JWT | 组织签发的用户 JWT（模块验签或问组织） |
| `X-Tenant-Id` | 只展示 | 不出现或忽略 | 必填，模块再问组织 |
| `X-Project-Id` | 只展示 | 当前项目 | 当前项目 |
| `X-Request-Id` | 建议 | 建议 | 建议 |

**不要**再增加 `/api/tenants`、`/api/projects` 这种无版本、无归属的根路径。过渡期现网可双挂，新代码只打 `/api/v1`。

路径里的 `{tenantId}` 只出现在 **org**。业务模块用 `{projectId}`（与组织项目 ID 相同），需要租户时走 Header。

**侧栏菜单（消费面，普通成员也要能读）**

| 方法 | 路径 | 鉴权 |
|---|---|---|
| GET | `/api/nav`、`/api/v1/nav` | 只要求登录 + 当前租户，**不是** `requirePlatform()` |
| GET | `/api/nav/groups`、`/api/v1/nav/groups` | 同上（与 `/api/nav` 同一个 controller） |

⚠️ 菜单读取**不能**挂在 `/api/v1/platform/*` 下：那一族全部要求平台管理员，普通租户成员的侧栏会永远是空的。
它按「当前租户已开通的模块」过滤 `nav_items`，并把产品的 `frontend_url`（服务登记里那份）一起带出来 ——
前端不必再查一次服务表。租户未选中时返回**空菜单**而不是报错。

分组元数据走**另一个**端点而不是并进 `/api/nav`：两者失败后果不同（菜单失败 = 侧栏少菜单，
分组失败 = 组顺序与空组策略回落到默认），合成一个响应会让这两种症状互相掩盖 —— 前端也是分两次拉的
（`stores/app.ts` 的 `Promise.allSettled`）。它也**不按许可过滤**：`always` 策略的要求正是
「模块未开通时这一组仍在、入口禁用并说明」，过滤掉就没法渲染了。

**租户工作台**

`T` 时没有 `{tenantId}` 这一段，改用 `/api/v1/users`、`/api/v1/projects`（本环境唯一组织）。`M` 必须带租户：

| 方法 | 路径 (M) | T 等价 |
|---|---|---|
| CRUD 用户 | `/api/v1/tenants/{tenantId}/users` | `/api/v1/users` |
| CRUD 项目 | `/api/v1/tenants/{tenantId}/projects` | `/api/v1/projects` |
| 模块策略 | `/api/v1/tenants/{tenantId}/modules` | （无） |
| 计算资源 | `/api/v1/tenants/{tenantId}/compute` | （无，或本环境一条 `/api/v1/compute`） |
| 授权码 | `/api/v1/tenants/{tenantId}/grants` | （无） |
| 外观 / LLM / 提示词 / 知识库 | `/api/v1/tenants/{tenantId}/appearance` 等 | `/api/v1/appearance` 等 |

**项目成员与产品角色（人仍在组织）**

| 方法 | 路径 |
|---|---|
| GET | `/api/v1/projects/{projectId}/members` |
| PUT/DELETE | `/api/v1/projects/{projectId}/members/{userId}` |
| PUT | `/api/v1/projects/{projectId}/members/{userId}/roles` body `{ product, role }` |

**内部（仅 M，供已登记模块；门禁是静态 `X-Module-Token`）**

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/internal/v1/authz/check` | query: `userId, tenantId, projectId, product, action` |
| GET | `/internal/v1/context` | 用户 JWT → 租户/项目/角色摘要 |
| GET | `/internal/v1/projects/by-code/{code}?tenantCode=` | **模块来拉项目镜像 + 许可**（见 §7） |
| GET | `/internal/v1/tenants/{tenantId}/compute` | 仓建设取 DS / 引擎连接 |

`tenantCode` 在 `by-code` 上是**必填**（缺了 400）：`/internal/v1/**` 没有 JWT，
回落到 `TenantContext` 就等于「让调用方决定查哪个租户」。查无此项目回 **404**，
调用方据此区分「组织说没有」与「组织不可用（503）」。

已删除：`POST /internal/v1/registry/heartbeat`（心跳退役）、
`GET /internal/v1/projects/{projectId}/bindings`（依赖心跳时代的探活表）、
`PATCH /api/v1/platform/services/{serviceId}`（无调用方）。

组织**不提供** `/api/v1/projects/{id}/domains|tables`。

## 7. 服务间调用（项目同步是**拉**，不是推）

```
浏览器 ──/api/v1──► 当前控制台同源 API
                      │
                      │  multi: Bearer module_token
                      ▼
                 组织 /internal/v1/authz/check
                 组织 /internal/v1/tenants/{id}/compute

模块 ──GET /internal/v1/projects/by-code/{code}?tenantCode=──► 组织
       （请求路径上按需触发，两条路：本地缺东西 → 同步拉；本地有、缓存过期 → 后台对账）
```

**组织不再知道模块的后端地址。** 改前是组织在建项目 / 改许可时 `PUT` 到各模块
（推送），那要求组织维护一张服务地址表、模块启动要心跳上报地址、还要处理「模块没起来时
推给谁」；而组织真正需要的只有模块的**页面地址**（门户要嵌它）。所以：推送与心跳一起删掉，
换成模块按需拉取。

- 组织登记的是 `service_registry.frontend_url`（**页面**地址，如 `http://127.0.0.1:5173`），
  不再是 `base_url`（后端地址）。那三列 `base_url` / `version` / `seen_at` 保留不删，只是没有写入源了。

### 7.1 两条触发路径（`required` 就是分岔口）

| | 触发条件 | 行为 | 失败 |
|---|---|---|---|
| **同步补齐** `required=true` | 本地**解析不出来**这一段租户/项目 | 请求线程直接去拉 | 组织不可达 → **503**（`组织平台不可用`）；组织说没有 → 沿用既有的 **400「编码未同步」** |
| **后台对账** `required=false` | 本地**有**镜像，只是正缓存过期了 | 丢给单线程后台队列，请求**不等**它 | 只记一行 warn + 落 15s 退避，**请求照常 200** |

**后台对账这条不能省，也不能改成同步**：它是「组织改了项目名 / 撤了许可，模块多久跟上」
的**唯一**通道。曾经只在「解析不出来」时才拉，结果是镜像一旦落地就**永不刷新**，
正缓存等同于死代码（实测：改项目名后模块一直显示旧名）。反过来把它放回请求路径上同步做，
就等于每个请求都可能为一次对账等 4 秒，且组织一抖动就把本来能正常服务的请求打成 503。

- 判据（`needsPull`）与模块自己的租户/项目解析**逐字一致**：`X-Tenant-Id: 1` 这种**数字本地 id**
  是既有合法用法，本地就有，不该每个请求都去打组织；更要紧的是组织不可达时本地能解析的请求
  **必须照常服务**（数据地图的核心能力不依赖组织）。所以判据是「这一段要不要问组织」，
  不是「项目在不在」。两处口径必须一起改，否则会出现「这边说解析得出来、那边说解析不出来」。
- 正/负缓存 **60s / 15s**，同一 key 的并发去重（`CompletableFuture` 单飞，后来者等同一个在飞的），
  短超时**连接 1s / 读 3s**（`OrgClient` 的 2s/5s 是给 `authz/check` 刻意设的，别混用）。
  **实测**：冷启动 20 并发打同一个新项目 → **只拉 1 次**，20 个请求全 200、总耗时 142~241ms。
- 失败语义分开，因为它们指向完全不同的排查方向：组织**说没有**（404）→ 落负缓存、调用方给 400；
  组织**不可达**（连不上/超时/5xx）→ 503 且**不落任何缓存**（否则组织抖一下就把正常项目钉死半分钟）；
  **根本没配组织地址** → 什么都不做（不落缓存、不抛异常），只在**第一次**留一行 warn
  —— 那是配置缺失，不该放大成整个模块 503，也不该每请求排一个空任务。
- **`tenantCode` 必填且不许回落 `TenantContext`**（org 侧新查询接口）：`/internal/v1/**` 没有 JWT，
  `TenantContext` 为空时 `requireProject` 会**跳过租户比对**，回落就等于跨租户取项目。

### 7.2 实测的传播与代价（2026-09-24 真机）

- **改项目名**：改名后模块在 **~60s**（= 正缓存 TTL）后自动跟上，期间**每一个请求都是 200**
  （后台对账不阻塞、不失败）。日志上能看见两行：请求线程的「从组织拉取项目镜像」+
  60 秒后 `project-refresh` 线程的同名行 —— 前者是同步补齐、后者是后台对账。
- **组织停机 → 恢复**（不重启模块）：本地能解析的请求全程 **200**；本地解析不出来的请求
  **503「组织平台不可用」**；组织回来后同一发请求自己变成 **200 / 400**，无需重启。
- **删项目**（pull 的真实代价，已知并接受）：见 `KNOWN_ISSUES` §9 —— 本模块**继续 200**
  地服务那个孤儿镜像（它没有许可表、也不问 `authz/check`），dw-model 则是 **403**。
- **撤许可**：靠正缓存 TTL 传播（同 60s）；`modules/aiCaps` 为 `null` 表示「组织没有这项信息，
  别动本地」，与空数组（组织说一项都没开通）走的是不同分支。

打开其它产品：组织给 `frontend_url + path`，不反代对方 `/api`（避免 cookie 串 origin 时还要再做一层）。
embed 页由对方自己读 `#boot=` 载荷（首次）与 `postMessage`（续期），详见 §12。

## 12. 门户集成：iframe 壳与消息协议

**形态**：组织是**壳**（`/org/embed/{product}/**` 里的 `<ProductEmbed>`），被嵌方是**子端**
（自己的页面 + `config/embed.ts`）。子端首次加载时从 URL 的 `#boot=` 拿登录态，
之后靠 `postMessage` 续期 —— 两条通道缺一不可：只留 `postMessage` 会让首次进入变成二次登录，
只留 `#boot=` 会在宿主静默换 token 后停在旧 token 上。

| 消息 | 方向 | 用途 |
|---|---|---|
| `dw-embed-ready` | 子 → 宿主 | 子端 `main.ts` 挂载完成，宿主可以推导航与 token |
| `dw-embed-navigate` | 宿主 → 子 | 切菜单时让子端 `router.push`，**不换 iframe** |
| `dw-embed-token-request` | 子 → 宿主 | 子端发现 token 快过期/已 401，主动要一次 |
| `dw-embed-token` | 宿主 → 子 | 新 access token |

**四条容易踩空的约束**：

1. **永不通配 `'*'`**：宿主与子端都先校 `event.origin`。子端的白名单 =
   boot 载荷里的 `hostOrigin` ∪ 运行期推导出的组织平台地址（`orgOrigin()`：
   `#boot=` 自报 → 后端 `/api/runtime` 答的 `orgUiUrl`（组织的**前端**地址，不是 `org-base-url`
   那个接口基址）→ 内置默认）∪ `document.referrer`。
   加 `hostOrigin` 是因为 `document.referrer` **不可靠**（跨域/策略/用户设置都可能为空），
   而白名单失效是**静默**的：token 推过去被丢弃，页面看起来只是「过一会儿就 401」。
   （2026-09-25 起不再读 `VITE_ORG_ORIGIN` / `VITE_WAREHOUSE_ORIGIN`，两个变量已删除。）
2. **`X-Frame-Options` / CSP**：Spring Security 默认 `DENY`，开发态（Vite 直接服务 SPA）
   完全看不出来，**打包态才白屏**。被嵌方的 `SecurityConfig` 要把 `frame-ancestors`
   设成宿主的 origin，且**白名单为空时保持 DENY**（fail-closed）。`cors.allowed-origins`
   里的端口通配（`http://localhost:*`）CSP 语法表达不了，会被丢弃并打 warn。
3. **切菜单不重建 iframe**：宿主的 `sessionKey` 只含 `{product, origin, tenantCode, projectCode}`，
   **不含 path**；sessionKey 不变且子端 ready 时走 `postNavigate`。所以别给
   `<ProductEmbed>` 加 `:key="route.fullPath"`，那会把整棵子应用重建一遍。
4. **别给 iframe 加 `referrerpolicy="no-referrer"`**：那会掐掉上面第 1 条里的 referrer 兜底。

**已知取舍**：iframe 目前**没有** `sandbox` 属性（全权限）。加 `sandbox` 需要同时列
`allow-scripts allow-same-origin allow-forms allow-popups` 等一长串，漏一项就是白屏，
而重前端产品很难逐个验证；本期**记录该决策**，不擅自加，等有明确威胁模型再补。
